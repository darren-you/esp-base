# FRP 正文早于接收准备

## 已观察到的问题

ESP32 的一次原生 FRP OTA 维护诊断中，`retire_inactive` 从开始到结束为 6.303141 秒，上传流在该阶段结束前已关闭；随后进入接收阶段只消费了 5,513 B。宿主已发送全部字节不能证明设备已消费。该操作按原 ID 核对为失败，原固件与生产配置保持。

实际固定的 FRP 0.2 源码 `0d9c08be7122ad73b0c24d912cf9b92a540ae3b2` 在 `forward_work` 中对排队正文无法继续写入本地连接使用 2,500 ms 停滞门。旧 Base 顺序为先预约并连接上传，再验证来源和退役 inactive，最后读取正文；准备期间本地接收缓冲可填满。

对同一固定 `work.c` 的 ASan／UBSan 宿主复现，注入 6,304 ms 不消费及假定 5,513 B 本地容量，提前发送在 2,550 ms 关闭；准备后再提供正文则转发完整 64 KiB。5,513 B 是复现假设，未测量真实 TCP 缓冲容量；这个假件结果与实板时序吻合，但不是全部硬件故障的唯一根因证明。

## 接收顺序

V4 写前意图仍在 worker 创建前持久提交并读回，来源完整验签、目标退役、选槽与失败清理保持。FRP start 返回 `accepted`，worker 先完成退役，再 arm 唯一上传槽。原 ID 查询在准备期返回 `accepted`，开放后返回 `running`；客户端核对同 boot 和完整原意图后才发送一次 PUT。开放后的 5 秒连接期限、FRP 停滞门和正文期限不变。

worker 重读并绑定原收据后，只向控制 owner 发布目标槽。当前活动请求的非终态查询据此返回精确元数据，避免在来源验签占用 Flash 时争抢收据读取；这不是缓存授权，也不能证明成功。worker 结束后仍通过持久收据与实际槽核对结果。

Server 准备查询共用原 30 秒写意图窗口，宿主工具共用原 10 秒窗口。旧 `running` start ACK 不作为新接收准备证明；任一观察丢失、身份错误或超时，后续不发送正文。USB URL 提交仍返回 `running`；本机 App 能解析其他入口产生的 `accepted` 原 ID 观察。

## 验证边界

生产 owner 的宿主回归注入 6,304 ms 退役、期间查询和失败，核对 arm 顺序、零额外 Flash 查询与原 5 秒等待。Go 的真实 TLS／HMAC fixture 核对准备期间没有 PUT、同一已验证上传连接只使用一次，以及错误 boot／操作／摘要／长度／目标／槽、取消和旧 ACK 的拒绝。Python 与 Swift 分别验证实际消费者。

上述软件修改尚不证明新候选可在实板升级。登记收据有时超过控制响应期限是另一已观测问题，不能由本修复推断消失；不得为此延长期限或在 unknown 后重发。需继续完成该问题的诊断、最终构建签名及双方协议组合的正式路径验收。动态进度与私有原件索引保留在 [#35](https://github.com/darren-you/darren-space/issues/35)。
