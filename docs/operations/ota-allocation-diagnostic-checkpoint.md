# ESP 原生业务、FRP 公网 OTA 与双目标容量验证

本文维护稳定技术合同、设计理由与固定验证方法。任务目标、动态清单、当前结论和阶段证据统一维护在根仓 Issue：[ESP 原生业务、FRP OTA 与双板最终交付](https://github.com/darren-you/darren-space/issues/35)。原执行记录按该 Issue 的迁移快照链接追溯，不在本文维护第二份进度。

## 当前能力与数据路径

| 所属对象 | 当前职责 |
| --- | --- |
| Base | 持久设备 UUID、配置、Wi-Fi／时间、管理协议、原生业务、升级协调和原 ID 结果 |
| FRP | 固定设备到 FRPS 的认证 TLS／TCP／Yamux 与既有双流预算，承载管理和完整固件字节 |
| MQTT | 认证管理、原生业务消息／结果、有限队列／outbox与重连 |
| OTA | 完整签名固件、摘要／芯片／项目／尺寸核验、A/B写槽与rollback；HTTPS和有界入站流共用机制 |
| Mac App | 实际本机 USB、设备核对与租约、本地协议操作，以及 Rust 核心／Swift 绑定的刷写与恢复 |
| Server／Web | 直接面向设备 FRP／MQTT 的远程管理与固件 OTA，固件身份和原 ID 对账 |

公网路径为调用方→官方 FRPS→设备 FRP→有界 OTA 接收→备用 app→验签／选槽／新 boot 本地确认→原 operation_id 持久结果，Mac／USB可离线。未经认证不创建意图或擦写；上传按固定缓冲顺序写入与背压，不把整镜像存入 RAM或新增Flash副本。数据流计入既有流预算；上传返回不等于持久成功，最终结果须在新boot查询，并独立核对完整固件身份。

本机有线路径为 Mac App→本地协议／Rust薄绑定→实际 USB→设备。当前 USB OTA 下发 URL，由设备 HTTPS 拉取；该路径不声称离线全 USB流式传输。直接刷写与首次分区装配使用当轮精确设备、安全状态、恢复基线与唯一租约，不能与应用 OTA 混同。两类 OTA入口共享单操作互斥、完整固件身份、30秒本地控制进展确认和原 ID结果；unknown只查原ID，不自动重发或另建操作。

设备 FRP连接／单次I/O／无进展／传输总期限为5／1／30／300秒；原status/restart的384 B／2秒解析边界保持。网络等待期间不持有短 Flash I/O claim，Flash擦写、槽观察及收据读回由既有owner裁决。MQTT／原生业务与FRP继续工作，不能停止网络来取得容量资格。

## 持久状态、分区与恢复

当前固件升级采用182 B V4收据，保留来源／候选精确签名身份、写前意图与读回、pending／VALID、自检、rollback、失败清理和原ID结果。普通升级遇旧V3、损坏或未决记录须阻断；旧格式只供一次性离线迁入解析，不能删除这段解析后把旧记录当空状态。真实配置、UUID、revision和有效凭据按已定语义保留。

C3／ESP32均为4 MiB Flash，双app各`0x1e0000`。C3保留11页`base_store`与`frp_scratch@0x3e5000`；ESP32保留六页`base_store`、`frp_scratch@0x3ea000`和只读旧AT原字节区。真实CSV见[固件说明](../../firmware/README.md)，一次性离线输入、官方验签、旧终态与归档读回见[OTA恢复合同](../../firmware/components/ota_operation/README.md)。应用OTA不修改bootloader或分区表。设备物理写入授权、安全状态和恢复基线仍按每轮真实目标核对，当前任务的云端删仓不授予设备写入资格。

## 容量预算与验收口径

| 项目 | C3／ESP32合同 |
| --- | --- |
| 内部堆 | INTERNAL\|8BIT历史最低值至少16,384 B |
| 连续空间 | 内部最大连续块至少24,576 B，并满足真实能力域下一最大合法申请 |
| 任务栈 | 每个真实任务最低余量至少1,024 B，包含网络、OTA、业务与SDK任务 |
| TLS／Wi-Fi | 证书、主机名和可信时间不降；IN16,384／OUT4,096 B、动态缓冲、12 sockets；静态RX／BA各6，动态RX／TX各32 |
| MQTT | 3.1.1／TLS、QoS／非retained命令；入站4,096 B、发布5,120 B、outbox16,384 B及原队列／在途预算 |
| FRP | 双活跃流与备用流、65,536 B最大控制记录、完整认证；OTA计入既有流预算 |
| 原生业务 | 消息字节计数、零字节、查询、暂停／恢复、定时状态、重启初始化；最大合法输入与真实背压 |
| OTA | 完整签名镜像、严格目标／长度、有界输入、A/B与rollback，网络和业务同存 |

历史最低堆、当前空闲、最大连续块、各region minimum与任务高水位分别报告；观察成本不加回，不把异时历史值拼成瞬时峰值，也不靠有限采样未遇峰值判定通过。双目标软件静态大小、普通／LAB候选与当前完整输入均记录在[软件检查点](native_software_checkpoint.md)，不据此推定实体资源或Flash寿命通过。

## 原生业务与 OTA 验收方法

### R1 原生业务与运行依赖

- 实现消息计数、二进制输入、暂停／恢复、非延期100 ms窗口和重启初始化的原生业务与确定性测试，输入由唯一控制owner同步消费。
- 解除动态运行引擎、包槽、产品账本、专属线程／队列和联合包升级；生产／样例／探针manifest、双锁、Kconfig与专属构包和测试入口已清理。
- 同步Tool真实UI／API、npm／Go依赖与持久字段，固件摘要改由独立状态链查询，保留设备身份、原ID和必要迁入解析。

### R2 固件独立 OTA 与恢复

- 保留签名、目标几何、摘要与A/B机制；接入有界入站流和本机URL型HTTPS来源。
- 实现V4写前读回、唯一operation、成功／失败／unknown和重启恢复，覆盖来源A、写入中断、待选C、pendingC、VALIDC与回滚A的宿主故障边界。
- 保留30秒本地控制进展、跨入口互斥和短Flash仲裁；旧记录／损坏／未决阻断和一次性离线迁入已有软件回归。

### R3 固件生产者与真实消费者

- 接通设备 FRP 的认证升级提交、完整固件流、进度及原 ID 结果查询；实现有界背压与各阶段期限，查询和数据流计入原流数／socket 预算。
- 完成公网升级端／Tool 到设备的新协议及真实客户端；固件字节必须经 FRPS／设备 FRP 工作流，不允许另走设备直连 HTTPS、USB 或局域网旁路取得该路径资格。
- 验证上述删除的实际运行与安装消费者：App沙盒启动不启动frpc、不开放远程Bridge或监听入口，本机操作与旧安装数据按已定合同保留；在最终Rust／App冻结候选上取得完整运行证据，不能以软件包静态检查替代。已核默认启动会操作真实安装容器并自动探测／打开匹配串口，没有受支持隔离启动参数，须与当轮设备／旧安装窗口一并验收；按维护者实板后置安排继续等待。本机USB／OTA／刷写恢复仍按下列实际设备项及R5验收。
- 验证 Mac App 本机实际 USB 设备的信息查询、控制、配置、OTA 提交／进度／原 ID 查询；完整 signed bin 身份与最终结果规则保持一致。另以实际 Rust 核心／Swift 绑定验证有线刷写／恢复，准确标明 URL 拉取的数据路径，不把 USB 发送命令当作全有线数据传输。
- 覆盖错误认证／重放／错设备、双入口并发、拒绝第二操作、截断／超长／错摘要／错签名、断流、慢读、超时、Flash／NVS 失败和结果丢失；未决只查原 ID，结束后资源可回收。

### R4 双目标分区与可复现构建

- 分别确定 C3／ESP32 的 4 MiB 新分区与首次有线迁入流程，移除 product_pkgs；验证双 app、otadata、base_store、FRP scratch、旧 AT 区及恢复边界，不将布局变更混入普通 app OTA。
- 完成两目标的独立 ESP-IDF／lwIP 嵌入式 SDK／组件锁、干净全量签名构建、官方验签、槽容量检查和 host/component 回归；构建只消费当前公开组件和精确SDK，不读取退役运行仓或隐藏实现。短Flash交接与集合读回两轮修复后，各自新71输入独立重建通过，最新双target完整host、前轮TSan与原失败分别保存；本项不包含 Rust 主机 SDK。

### R5 C3 与 ESP32 实体容量和故障验收

- 每块板分别核对身份、芯片、4 MiB、安全状态、当轮恢复基线与唯一设备租约；未连接的 ESP32 保留外部前置，不用模拟器或 C3 数字代替。
- 在真实 Wi-Fi、TLS MQTT、官方 FRPS 和原生业务同时工作时，通过公网完成一份完整签名镜像 OTA、重启、原 ID 持久成功及再次重启查询；拔除 Mac 数据连接后仍能完成公网路径。
- 覆盖 MQTT 最大输入／满合法队列／在途／outbox、FRP 双流／备用流／最大控制记录，与 OTA 建连、传输、擦写、验签、NVS 提交及原生业务最忙阶段的合法重叠；分别满足 16,384／24,576／1,024 B 门，无非预期 OOM、overflow、失联或资源泄漏。
- 核对全任务栈、各实际内存能力域与最大后续申请，验证长／短 Flash owner 不互相等待；测量 FRP scratch、OTA 和配置写入的联合最坏延迟，回归历史 FRP 超时及相关 SDK 接收边界。
- 两板分别完成真实断电／复位：意图写入、擦写中、校验后选槽前后、pending、自检确认、成功收据前后；验证仍可启动正确镜像、查询原结果或如实 unknown，损坏镜像不获选。
- 两板分别复验 Mac App 本机信息／控制／配置／OTA，以及经已冻结 Rust 核心和 Swift 绑定执行的有线首次装配／刷写和恢复。覆盖 Mac／App／USB 离线、切换目标、多设备和身份不符；不误写或虚报成功，设备 FRP 与本机 USB 操作互斥，原生业务与设备配置按已定语义保留；确认 App 不再启动 frpc 或开放远程 Bridge。本项验证 App 实际消费能力，不代替独立 SDK 全矩阵验收。

### R6 双板长稳与 Flash 使用目标

- 在相同已通过 R5 的候选上，每板完成 100 次网络／业务／升级相关生命周期及资源回收检查；记录实际循环组成和成功／失败清理，不用宿主循环代替实体结果。
- 每板完成 72 小时原生业务、MQTT、FRP 与定期公网 OTA 联合长稳，记录断线恢复、操作终态、堆／连续块／栈趋势；不得把多次独立短测相加冒充连续长稳。
- Flash 设计使用目标定为 5 年；超过 4 KiB 的 FRP 加密控制记录按长期平均最多每小时 1 次计算，约 43,830 次 scratch 擦写，另计启动、失败重试及其他写入。该频率是工程假设，不是已经实现的限流；须按两板实际 Flash 规格、热点扇区与实测开销核算，超出假设时重新计算。普通 TCP 固件数据不按该类控制记录计数，不能按心跳或固件每个数据块虚增 scratch 寿命消耗。

## 正式交付条件

最终候选由保留仓及锁定 ESP-IDF／lwIP 完成干净双目标签名构建／验签；固件运行输入、客户端、实际依赖与正式信任一致。原 ID 结果、公网独立路径、Rust／Swift 实际有线刷写恢复、旧安装保留、双板故障／百次／连续72小时形成完整资格。软件原件或历史组合结果不授予新实体候选资格。
