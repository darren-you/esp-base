# 配置候选断电验收

2026-09-22，在既有迁移基线对应的同一块 ESP32-C3 / 4 MiB 板卡上，通过了一次 RAM 候选配置验证期间的人工 USB 断电与恢复。没有刷写固件，也没有执行恢复写入；本次不证明 NVS 实际编程中间态掉电。

## 制品与前置条件

运行既有 P2 应用，760576 字节，SHA-256 为 `5097fb549ff792680a311144b44340f5470a78bcd11b3694d29e77d07d684773`。原配置 revision 为 5。监测使用公开 `tools/device-control.py` 的 POSIX 串口实现，持有 Bridge 共用端点租约，不切换 DTR/RTS；先停止该端点的原 Mac Bridge。

本轮按 USB 枚举定位设备，再读取协议 UUID、revision 与 Wi-Fi 状态。两次新鲜的完整 Flash 读取一致，并逐字节等于既有已核验的恢复基线，因此同时确认应用、身份、配置、分区与 OTA 选择保持原值。只读 esptool 操作的复位发生在人工断电观测区间之外。

## 实际观测

1. 通过 USB 发送一次完整 `config.set`，精确绑定当前 UUID、boot、revision 5 和有效期限；候选使用随机生成的不存在测试网络，无生产凭据。
2. 收到同设备、同 boot、同请求的 `running` 回执后，提示维护者拔除 USB 电源。请求发送至枚举确认设备消失为 12.171 秒，位于固件的 20 秒候选窗口内；消失前收到的该请求回执只有 `running`，没有提交或失败结果。
3. 设备消失 7.482 秒后重新枚举到相同物理设备。不开启会额外复位的串口控制线操作，读取到新 boot 的 `reset=power_on`、原 UUID、revision 5 和 Wi-Fi `connected`。
4. 恢复后再次读取两份完整 Flash；两者均与本轮断电前的两份基线逐字节相等。身份、配置、所有应用槽及其他分区均未改变，无需写回恢复件。
5. 只读核对结束后再次确认原 UUID、revision 5 与 Wi-Fi 连接，并以进程路径及端点占用验证原 Mac Bridge 已恢复监控。

这些结果证明本轮 RAM 候选未持久化，断电后从原提交配置启动。USB 消失时间来自宿主枚举轮询，不是电源示波器测量；`power_on` 来自本次新 boot 的真实设备报告。

## 失败尝试与证据边界

首次准备后，串口在发送候选前返回 `ENXIO`（Device not configured）。没有生成或发送候选请求，因此不计入候选断电通过次数；错误、基线与原始日志保留。重新枚举并重新读取双份完整基线后执行上述有效尝试，没有把失败覆盖成成功。

真实 UUID、USB 序列号、配置输入、完整 Flash、原始日志与执行脚本只保存在 ESP Tool 私有忽略目录：首次尝试为 `p2-candidate-power-20260922/`，有效尝试为 `p2-candidate-power-retry-20260922/`。目录权限 0700，文件 0600；公开记录不包含恢复字节或网络身份。

已提交配置断电恢复另见[开发检查点](development_checkpoint.md)。本次只关闭 RAM 候选期间断电子项；Flash 实际写入中间态掉电、WPA3、外部 AP 中断、完整 USB 插拔矩阵和五能力长稳仍未完成，P2 整体保持实施中。
