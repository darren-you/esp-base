# C3 `base_store` 异常页只读分类

## 输入与方法

2026-09-27 只读取 P1-04 在 `mac-pro-1` 私有目录保全的两份 C3 完整 4 MiB Flash；两个不同的普通文件均为私有权限，长度相同且逐字节一致。原文件、设备和分区均未写入，也未生成 v3 候选。分析时没有输出原始字节、设备身份、配置值、文件名或私有镜像摘要。

NVS 状态由本仓锁定的 ESP-IDF `578cf89c343e388db43ba1f4ddcd602fedcb763c` 官方 `nvs_partition_tool/nvs_parser.py` 判定；工具源码工作树检查为干净。解析器源码经标准输入在备份宿主内存中执行，以推迟类型注解求值适配宿主 Python 3.9，没有改变解析逻辑或移动私有镜像。逐页字节统计、页/块 SHA-256 相等比较只在同一份完整备份的内存中执行；以下只公布分类、计数和相对页号。

`base_store@0x3e0000/0x20000` 共 32 个 4 KiB 页，表中页号从分区起点算。第 0 页为官方解析器确认的 Active、版本 2、页头 CRC 正确；现行[离线迁移预检](base-v3-offline-migration.md)已单独核对其中 v1 配置。第 1–31 页的页状态均为 Invalid，页头 CRC 均不匹配；这不等于已经证明原来是损坏的 NVS 页，也不意味着可以擦除。官方解析器对无效页解释出的条目状态不作为业务记录证据。

## 结论边界

现物能够证明：第 0 页有可读 v1 业务配置，后 31 页不是当前固定 SDK 可审计的有效 NVS 页；其中大量字节与旧 `ota_1` 字节重合，但 27 页没有整页对应。因此既不能把所有异常页归类为 `0xff` 空闲区，也不能把它们确认为可丢弃的旧应用残留。没有写入时间线、旧固件精确源码与写入日志，无法给出来源或处置授权。

完整 `base_store` 的 v3 离线预检继续阻断。现有 QEMU 同键保页探针仅证明一次正常提交未触及后 31 页，不能保证以后换页不擦除；本检查点没有修改该探针或改变首次迁移条件。若要处置这些历史字节，仍须由维护者在完整恢复、后续 NVS 写入和双槽签名启动方案具备可验证结果后决定保存边界。
